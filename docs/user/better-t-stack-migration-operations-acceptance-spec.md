# Better T Stack + SQLite データ移行・運用・受入仕様書

## 1. 目的と前提

本書は、現行 PostgreSQL/Go 環境から Better T Stack/SQLite 環境へデータを安全に移行し、継続運用・受入・ロールバックを行う手順と判定基準を定義する。

移行対象は `links`、`access_logs`、画像、APK である。認証情報は移行しない。新環境で初期管理者を作成する。移行元 `links` テーブルの完全 DDL はリポジトリで確認できないため、実施前に必ず取得・承認する。

## 2. 実装時の成果物

| 成果物 | 必須内容 |
| --- | --- |
| `drizzle` migration | 認証テーブルを含む全 SQLite schema、制約、索引、ロールバック可能な変更方針 |
| `export-postgres` | 読み取り専用接続でリンク・アクセスログを JSON Lines または CSV へ出力。実行日時・件数・元 DB 識別子を記録 |
| `import-sqlite` | バリデーション、タグ正規化、トランザクション投入、ID 対応表、再実行可能性 |
| `migrate-uploads` | ファイル hash、UUID 保存名へのコピー、DB レコード生成、失敗一覧 |
| `verify-migration` | 件数、タグ、ファイル hash、統計、例外の照合レポート |
| `seed-admin` | 初期管理者の安全な一回作成。詳細はセキュリティ仕様書に従う |
| backup/restore script | DB と uploads を同一世代で退避・復元し、整合性を検証 |
| runbook | デプロイ、監視、障害対応、ロールバックの手順 |

すべてのスクリプトは dry-run を備え、秘密情報を出力せず、終了コードと機械可読な結果 JSON を返す。

## 3. データ変換仕様

### 3.1 links

| 移行元 | 移行先 | 変換 |
| --- | --- | --- |
| `id` | `links.id` | 既存 ID を維持する。SQLite sequence を移行最大 ID へ合わせる |
| `title` | `title` | UTF-8 とトリムを検証。空文字はエラー一覧へ出力して投入しない |
| `url` | `url` | HTTP/HTTPS URL を検証。不正値はエラー一覧へ出力して投入しない |
| `image` | `image_upload_id` または null | 既存画像 URL をファイル名へ解決し、コピー成功後の upload ID を設定。外部 URL は移行せず null として例外一覧に出す |
| `description` | `description` | null/文字列を維持。上限超過はエラー |
| `tags` | `tags` + `link_tags` | 3.2 の規則で分解・統合 |
| `visible` | `visible` | null は true とする |
| `created_at`/`updated_at` | 同名の epoch ms | UTC に変換。不正日時は移行実行を失敗させる |

### 3.2 タグ

1. 移行元の tags 配列を順に読み込む。
2. 各要素を Unicode NFC 正規化、前後トリム、連続空白圧縮、Unicode 小文字化する。
3. 正規化後が空文字なら破棄し、警告として記録する。
4. 同じ `normalized_name` は 1 つの `tags` レコードへ統合する。表示名は移行順で最初のトリム済み文字列とする。
5. 同じリンクの重複タグは 1 件に統合する。

### 3.3 access_logs

| 移行元 | 移行先 | 変換 |
| --- | --- | --- |
| `id` | `access_logs.id` | 既存 ID を維持する |
| `link_id` | `link_id` | 対応する移行済みリンクがなければエラー |
| `accessed_at` | `accessed_at` | UTC epoch ms |
| `user_agent`/`referer` | 同名 | 2,000 文字で切り詰め、制御文字を除去 |
| `ip_address` | `ip_address_hash` | 既存生 IP は移行しない。null を格納し、例外一覧で件数を記録する |

`ACCESS_LOG_RETENTION_DAYS` より古いログは投入しない。除外件数と最古・最新日時をレポートへ記録する。

### 3.4 ファイル

- 移行元の `uploads/images` と `uploads/apk` を再帰走査し、シンボリックリンクは拒否する。
- ファイルは形式・サイズを再検証し、SHA-256 を計算する。
- 保存先は UUID 名にし、元のファイル名、MIME、サイズ、hash、作成日時をレポートへ記録する。
- 画像は `links.image` の URL/ファイル名に対応するものだけ `image_upload_id` に関連付ける。孤立画像も `uploads` に保持するが、レポートで孤立として示す。
- APK とリンク URL の対応が現行 DB では保証されない。`/api/apk/download/{filename}` に一致する URL だけを新 URL に変換する。その他は外部 URL として維持し、存在しない APK 参照はエラーにする。

## 4. 移行手順

### 4.1 事前条件

1. 現行 PostgreSQL の schema-only dump と data-only dump を取得する。
2. `links` の列、NULL 可否、デフォルト、制約、トリガー、インデックス、実行件数を移行マッピングに照合して承認する。
3. DB dump、uploads、環境変数の安全なバックアップを取得し、復元できることを確認する。
4. 検証環境で全手順を少なくとも 1 回成功させる。

### 4.2 検証移行

1. 空の SQLite DB に migration を適用する。
2. `seed-admin` を実行する。
3. `export-postgres --dry-run`、`migrate-uploads --dry-run` で不正データ・ファイルを報告する。
4. export、ファイルコピー、SQLite import を実行する。
5. `verify-migration` と E2E テストを実行する。
6. 発見した例外は、修正、許容、除外のいずれかを責任者が承認する。

### 4.3 本番切替

1. メンテナンス開始を告知し、現行環境のリンク変更・アップロードを停止する。
2. 最終 PostgreSQL dump と最終 uploads スナップショットを取得する。
3. 検証済みと同じバージョンのスクリプトで移行・照合する。
4. 受入判定が通った場合にのみ、リバースプロキシ/DNS を新環境へ切り替える。
5. 切替後にログイン、リンク表示・作成、画像・APK 取得、クリック集計、バックアップを確認する。
6. 旧環境は読み取り専用で 30 日間保持する。

## 5. 照合・受入基準

| 対象 | 基準 |
| --- | --- |
| links | 有効な移行元リンク数と移行先数が一致する。除外がある場合は ID・理由・承認者を全件記録する |
| tags/link_tags | 正規化後のユニークタグ数、各リンクのタグ集合が変換規則どおりである |
| access_logs | 保持期間内の有効ログ件数が一致する。生 IP を移行しない件数を記録する |
| uploads | 対象ファイル数、サイズ、SHA-256 が一致する。孤立・不正・欠損ファイルは例外として承認済みである |
| 統計 | 総クリック、今日/7日/30日、上位 10 リンクが時刻差を考慮した期待範囲で一致する |
| 認証 | 初期管理者のログイン、匿名/ viewer の管理拒否、管理者の操作許可が成功する |
| DB | 外部キー有効、migration 再適用時に失敗しない、バックアップから空環境へ復元できる |
| UI | 公開検索、タグ絞込み、リンク CRUD、画像/APK、分析、JSON export の E2E が成功する |

移行後の件数差分はゼロを原則とする。保持期間によるアクセスログの除外、生 IP の非移行、無効な URL/ファイルの除外だけは、明細と承認がある場合に許容する。

## 6. 運用手順

### 6.1 デプロイ

- ビルド済みイメージと lockfile により依存バージョンを固定する。
- deploy 前に schema migration、DB バックアップ、ヘルスチェックを順に実行する。
- migration に破壊的変更がある場合は、expand → deploy → backfill → contract の複数リリース方式を採用する。
- アプリケーションは 1 レプリカで稼働する。水平スケールが必要になった場合は SQLite 継続可否を再評価する。

### 6.2 バックアップと復元

- 日次バックアップを最低 30 世代保持する。DB と uploads の世代 ID を一致させる。
- deploy 前に追加バックアップを実行する。
- 月次復元試験で別環境へ復元し、DB integrity check、管理者ログイン、公開リンク、画像、APK を検証する。
- DB 破損時はアプリを停止し、最新の整合した DB と同世代の uploads を復元する。WAL だけを個別に復元しない。

### 6.3 監視

| 項目 | 警告条件 |
| --- | --- |
| アプリ健全性 | HTTP health check の失敗 |
| DB | `integrity_check` の失敗、DB 容量の異常増加、ロック待機超過 |
| uploads | 空き容量 20% 未満、アップロード失敗率上昇 |
| 認証 | ログイン失敗・rate limit の急増 |
| バックアップ | 日次バックアップ失敗、復元試験未実施 |

## 7. ロールバック

次のいずれかが起きた場合、切替責任者は旧環境へロールバックする: ログイン不能、公開リンクの重大欠損、画像/APK 配信不能、承認されていないデータ照合差分、バックアップ失敗。

1. 新環境への書込みを停止する。
2. 新環境で生じたリンク変更、uploads、アクセスログを退避する。
3. リバースプロキシ/DNS を旧環境へ戻す。
4. 旧環境が正常に稼働することを確認する。
5. 新環境の障害記録、退避データ、再切替条件を作成する。

SQLite から PostgreSQL への自動逆同期は実装しない。ロールバック後に新環境の書込みを旧環境へ反映する必要がある場合は、承認済みの手動データ補正手順を別途作成する。

## 8. 実装・切替を停止する条件

以下が未解決の場合、実装の基盤構築は可能でも、データ移行・本番切替を進めてはならない。

- 現行 `links` テーブルの完全 DDL とデータプロファイルが未取得。
- [機能・API・データ仕様書](better-t-stack-functional-api-spec.md) の D-01〜D-06 が未承認。
- 本番の永続ストレージ、バックアップ保管先、復元責任者が未決定。
- SQLite を複数 writer で運用する要件があるが、代替 DB 方針が未決定。
